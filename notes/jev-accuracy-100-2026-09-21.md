# Jev accuracy comparison: 100 situations, 21 September 2026

**Jev improved final app answer decisions from 87/100 to 89/100 on this fixed synthetic stress set. All three repetitions produced the same scores and the same two improvements. No paired regression was observed.** This is a modest gain, not evidence of broad superiority across real interviews.

## What was measured

The primary score is whether the **real processor answers a complete information request, or withholds an answer for a statement, filler, or incomplete utterance**. An error/empty-answer output counts as failure. It is not answer-content correctness, transcription accuracy, or an unrestricted five-way model-label accuracy score. Buffering of incomplete speech is additionally checked from processor logs.

There are 100 unique text fixtures with expected labels and rationales fixed before the calls. Each was replayed three times with Jev off and three times with Jev on: 600 processor turns, 300 per configuration. The fixture SHA-256 is recorded in `.codex-loop/jev-accuracy-100/manifest.json`; the scorer verifies it. Expected labels were never supplied to either model.

The harness links the current production processor and clients. Groq transcription is replaced with the supplied fixture text, and the existing direct Groq answer path returns a placeholder, because this test evaluates answer triggering rather than answer content. The combined xAI classifier and Jev call the real APIs. Real local filtering, fast-path selection, candidate vetoes, buffering, and classification overrides execute. Per-case processors isolate cooldown and duplicate state. Contextual follow-ups receive the stated prior utterance/topic.

## Results

| Outcome | Jev off | Jev on |
|---|---:|---:|
| Correct final actions | 261/300 (87%) | 267/300 (89%) |
| False answers to non-questions | 30 | 24 |
| Missed complete questions | 6 | 6 |
| Error/empty-answer outputs | 3 | 3 |
| Incomplete utterances correctly buffered | 18/30 | 24/30 |

All three passes individually scored 87/100 versus 89/100. The 300 observations per mode are repetitions of 100 cases, not 300 independent situations. Each case has equal weight; these percentages are **not estimates of real-world prevalence-weighted accuracy**.

Sixty of the hundred cases reached the ambiguous classifier path; forty were handled locally. On the classifier-reaching subset, final-action scores were 153/180 (85%) versus 159/180 (88.3%). Jev was called 180 times; no Jev unavailable events were logged. Its initial acceptance log is emitted before the processor's strong-local-signal fallback check, so it must not be treated as proof that every confident Jev label controlled the final action.

## Exactly what improved

Two incomplete prompts were answered prematurely with Jev off and correctly buffered with Jev on in all three repetitions:

- “If the service goes down while”
- “The question I want to ask is whether”

That is a 20-percentage-point gain on this ten-case incomplete-speech slice (6/10 to 8/10), and a two-percentage-point gain across the complete set. Both metrics refer to this deliberately balanced synthetic set.

## What did not improve

Eleven cases still failed in both configurations. Examples:

- “I wonder how you would handle duplicate messages.” Both paths return question, but the shared candidate-statement veto suppresses the answer.
- “My main responsibility was maintaining Playwright tests.” A local fast path triggers an answer, so Jev is bypassed.
- “Your explanation was clear, thank you.” The shared language-marker list treats English “was” as a German question marker. It promotes a statement to an answer flow that has no answer text.
- Quoted or retracted questions still confuse shared local rules; neither configuration improved that category.
- “How would you” and “Tell me about a time when you” still receive premature answers.

All ten Bulgarian/mixed-language questions passed in both modes. No mixed-language accuracy improvement was demonstrated. Shared-rule evidence is in `Application/VoiceInterviewProcessor.swift:390`, `Application/VoiceInterviewProcessor.swift:928`, and the per-case run log.

## Accuracy versus latency

The separate [direct API performance trial](jev-direct-performance-2026-09-21.md) measured about 17% longer median time to the first 40 answer characters on two ambiguous question prompts. This 100-case trial did not remeasure that latency percentage across the broader corpus.

If preventing premature answers is worth a modest delay, these results support an **optional accuracy-focused pilot**. They do not justify saying Jev is broadly more accurate at every decision. Most remaining failures live in shared local rules; fixing those may improve both configurations without a new network call. Keep the fixture and acceptance thresholds unchanged while evaluating those fixes to avoid tuning the benchmark into a success.

## Limits, evidence, and reproducibility

Fixtures and expected answers are assistant-authored synthetic examples, not independent human-labeled recordings or a blind benchmark. There is no acoustic noise, actual microphone capture, native UI evaluation, long-session concurrency, or full assessment of topic/context retention. The incomplete buffering check reads existing log events; it does not test every subsequent speech continuation. Generation quality was not scored. There are only two distinct Jev wins, so repeated consistency should not be mistaken for many independent improvements.

Artifacts under `.codex-loop/jev-accuracy-100/`: `cases.json`, `manifest.json`, `evaluate.swift`, `build.sh`, `results.json`, `annotated-results.json`, `run.log`, `score.py`, and `summary.json`. Some concurrent emoji log writes required replacement decoding for analysis; the primary JSON results are written atomically and decode normally.

To reproduce, compile with the artifact `build.sh`, then run `evaluate` from that directory with `IM_RUN_LIVE_CLASSIFICATION=1 IM_JEV_ENABLED=1`. The harness resumes any completed entries in `results.json`; use a new output directory or preserve/rename prior results for a fresh trial. Private keys are read without printing them. The app preference and production source were not changed; all feature enabling was confined to the evaluation process.
